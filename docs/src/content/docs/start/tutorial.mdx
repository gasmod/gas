export const local = (src) => src.replaceAll(MODULE, 'example.com/notesapi');

export function stage(src, hide, added) {
	const lines = [];
	const ins = [];
	let skipping = null;
	let inAdded = false;
	for (const line of src.split('\n')) {
		const t = line.trim();
		if (skipping) {
			if (t === `// #endregion ${skipping}`) skipping = null;
			continue;
		}
		const open = t.match(/^\/\/ #region (\S+)$/);
		const close = t.match(/^\/\/ #endregion (\S+)$/);
		if (open && hide.includes(open[1])) {
			skipping = open[1];
			continue;
		}
		if (open) {
			if (open[1] === added) inAdded = true;
			continue;
		}
		if (close) {
			if (close[1] === added) inAdded = false;
			continue;
		}
		if (t === '' && lines.length && lines[lines.length - 1].trim() === '') continue;
		lines.push(local(line));
		if (inAdded && t !== '') ins.push(lines.length);
	}
	while (lines.length && lines[lines.length - 1].trim() === '') lines.pop();
	return { code: lines.join('\n'), ins };
}

This tutorial builds a small JSON API for notes, from an empty directory to a
tested app. Each client authenticates with an API key and sees only its own
notes. The data lives in a SQLite file, so there is nothing to install beyond
Go.

Along the way it uses the Gas core (services, routing, handlers, errors) and
five modules: [config](/gas/modules/config/), [logging](/gas/modules/logging/),
[database](/gas/modules/database/), [migrations](/gas/modules/migrations/), and
[auth](/gas/modules/auth/). Each step ends with something to run, and links to
the page that covers its pieces in depth.

You need Go 1.27.3 or newer (see [Installation](/gas/start/installation/)) and
`curl`. The finished project looks like this:

## Step 1: create the project

Create a module and add the Gas packages this tutorial uses, plus the pure-Go
SQLite driver:

```bash
mkdir notesapi && cd notesapi
go mod init example.com/notesapi
go get github.com/gasmod/gas \
  github.com/gasmod/gas/config \
  github.com/gasmod/gas/log \
  github.com/gasmod/gas/database \
  github.com/gasmod/gas/migrate \
  github.com/gasmod/gas/auth \
  modernc.org/sqlite
```

The core and each module are separate Go modules, so an app adds only the ones
it uses.

`LoadConfig` reads `config.json` first and the environment second. A later
provider overrides the keys it defines, so an environment variable wins over
the file: `KEYS__ADMINTOKEN` sets `Keys.AdminToken`, with `__` separating the
levels. Reading from disk, the JSON provider only opens files inside the
working directory, so run the app from the project root. See [Config](/gas/modules/config/) for the
providers and the naming rules.

`New` registers two things in the container:

- the loaded config, as a ready-made instance under `gas.ConfigProvider`. The
  app binds its own settings from it at startup (here `GasEnv`, `Server.Host`,
  and `Server.Port`), and the modules added in later steps bind their sections
  from it.
- a logger under `gas.Logger`. `gaslog.NewSlogLogger()` writes through the
  standard library's `log/slog`. See [Logging](/gas/modules/logging/).

The request logger middleware logs each request's method, path, status, bytes
written, duration, and remote address: at error level when the status is 400
or above, at info level otherwise. Its request ID field is turned off because
the ID comes from chi's `RequestID` middleware, which this app does not mount.

## Step 3: add the database and migrations

Two modules go into `New`: the database connection and the migration manager.
The highlighted lines are new.

<Code code={app2.code} ins={app2.ins} lang="go" title="app/app.go" />

`database.New()` reads the `Database` section of the config when it
initializes. `Driver` is the `database/sql` driver name, and `"sqlite"` is the
name `modernc.org/sqlite` registers. `gas/database` does not import a SQLite
driver itself, which is what the blank import is for. `DSN` is the file to
open, relative to the working directory. The service opens the database and
pings it, and startup fails if it cannot.

`MaxOpenConns` and `MaxIdleConns` are both `1`: with one connection, queries
take turns instead of contending for SQLite's write lock. `MaxIdleConns` must
be between 1 and `MaxOpenConns`. See [Database](/gas/modules/database/) for
every key and its default.

`migrate.New()` takes the `gas.DatabaseProvider` and, when it initializes,
creates the `__gas_migrations` table that records what has been applied.
Services register their migrations with it during their own `Init`; once every
service is initialized, `Start` applies the pending ones in version order. See
[Migrations](/gas/modules/migrations/).

<Aside type="caution" title="Register migrate under gas.MigrationManager">
`Start` looks the migration manager up as `gas.MigrationManager`, and the
modules that own tables take a `gas.MigrationManager` in their constructors.
Registered under `*migrate.Service` instead, it is invisible to both: `Start`
runs no migrations, and the API key service added in step 4 fails to build:

```text
building apikey.Provider: resolving dep gas.MigrationManager for apikey.Provider: no registration for gas.MigrationManager
```
</Aside>

## Step 4: issue API keys

Clients will authenticate with API keys, which `gas/auth/apikey` generates,
stores, and checks. Something has to hand them out, so the first service is a
small one: `POST /keys` creates a key for a subject, and only callers that
present the admin token from the config may use it.

<Code code={local(region(keysSrc, 'service'))} lang="go" title="keys/service.go" />

This is the shape of every Gas service. `New` is a plain constructor, and the
container supplies its parameters: the router, the config, and the API key
provider. `Name` identifies the service in logs and in the route map, and
marks it as the owner of its routes. `Init` runs once at startup; this one
binds its part of the config and registers its route. `Close` runs at shutdown
and has nothing to release here. See [Services and DI](/gas/core/services/).

`Bind` fills `Config` from the loaded config and checks its `validate` tags. A
missing admin token, or one shorter than 16 characters, stops startup:

```text
building *keys.Service: init *keys.Service: keys: config: validate config: Key: 'Config.Keys.AdminToken' Error:Field validation for 'AdminToken' failed on the 'min' tag
```

The handler completes the file:

<Code code={local(region(keysSrc, 'create'))} lang="go" title="keys/service.go" />

A handler that takes `gas.Context` and returns `error` is a DI-aware handler.
A returned `*gas.Error`, such as the one `gas.Unauthorized` builds, is written
as a JSON error at its status. `BindJSON` decodes the body and runs the
`validate` tags. `Generate` returns the plaintext key once; the database keeps
its SHA-256 hash and its first 8 characters, not the key. See
[Handlers and Context](/gas/core/handlers/) and [Errors](/gas/core/errors/).

Register the API key provider and the new service:

<Code code={app3.code} ins={app3.ins} lang="go" title="app/app.go" />

`apikey.New()` takes a `gas.DatabaseProvider`, `gas.Logger`,
`gas.MigrationManager`, and `gas.ConfigProvider` from the container. In `Init`
it reads the `APIKey` section of the config (nothing to set here: the header
defaults to `X-API-Key`) and registers its own migrations for the configured
driver, which create its table. It is registered under the `apikey.Provider`
interface, and the services that use it ask for that type. See
[Auth](/gas/modules/auth/).

The notes service owns a table and four routes. Start with its schema, as a
pair of migration files:

<Code code={downSQL} lang="sql" title="notes/migrations/20261021001_create_notes.down.sql" />

A migration file is named `{version}_{description}.up.sql`, and every `.up.sql`
needs a matching `.down.sql`. The version is everything before the first
underscore. Versions from every service are applied in one global order, so a
timestamp keeps them unique.

The service embeds those files and registers them, then registers its routes
behind the API key middleware:

<Code code={local(region(notesSrc, 'service'))} lang="go" title="notes/service.go" />

Because `New` takes an `apikey.Provider`, the container builds the API key
service before this one. `RegisterFS` reads the embedded files and registers
them as migrations owned by this service; `Start` applies them after every
`Init` has run.

`auth.Middleware` authenticates each request with the API key provider, which
reads the key from the `X-API-Key` header. On success it puts the principal on
the request context and calls the handler. On failure it calls the
`WithOnError` function, which here writes the same JSON error shape the
handlers produce; without `WithOnError`, the middleware writes a plain-text
401. The middleware is added inside `Route("/notes", ...)`, so it applies to
the notes routes and not to `POST /keys`. See [Routing](/gas/core/routing/)
and [Middleware](/gas/core/middleware/).

```bash

  -d '{"title":"First note","body":"Hello from Gas"}'
curl -X POST localhost:8080/notes -H "X-API-Key: $KEY" \
  -d '{"title":"Second note","body":"SQLite underneath"}'
```

```json
{"id":1,"title":"First note","body":"Hello from Gas","created_at":"2026-10-21T16:05:42.844152Z"}
```

```bash
curl -X POST localhost:8080/notes -H "X-API-Key: $KEY" -d '{"body":"no title"}'
```

```json
{"error":{"status":422,"code":"validation_failed","message":"request validation failed","fields":[{"field":"title","rule":"required","message":"is required"}]}}
```
