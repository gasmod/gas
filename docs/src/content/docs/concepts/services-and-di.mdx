Services are registered with the DI container through constructors. The
container resolves dependencies, topologically sorts them, validates lifetime
rules, and calls `Init(ctx)` on every `Service` it holds.

## Registering

```go
gas.WithService[*auth.Service](auth.New, gas.ServiceLifetimeSingleton)
```

Shorthands infer the lifetime from the name:

```go
gas.WithSingletonService[*auth.Service](auth.New)
gas.WithScopedService[*RequestLog](NewRequestLog)
gas.WithTransientService[*Nonce](NewNonce)
```

Pre-built values are registered as instances and treated as singletons.
Pre-built means pre-constructed, not pre-initialized: if the value implements
`gas.Service`, the container still calls `Init(ctx)` at startup and `Close(ctx)`
at shutdown, so do not call `Init` yourself first.

```go
gas.WithServiceInstance[gas.ConfigProvider](cfg)
```

## Register under the type your consumers ask for

The type parameter is the key the service is stored under, and lookups are by
**exact type**. The container deliberately does not scan its registrations for
something that happens to satisfy an interface, because that search is ambiguous
as soon as two services implement the same one.

<Tabs>
<TabItem label="Fails at startup">
```go
// migrate asks for gas.DatabaseProvider, but the database is registered
// under its concrete type.
gas.WithSingletonService[*database.Service](database.New())
gas.WithSingletonService[*migrate.Service](migrate.New())
```

```
building *migrate.Service: resolving dep gas.DatabaseProvider for *migrate.Service:
  no registration for gas.DatabaseProvider
```
</TabItem>
<TabItem label="Works">
```go
gas.WithSingletonService[gas.DatabaseProvider](database.New())
gas.WithSingletonService[gas.MigrationManager](migrate.New())
```
</TabItem>
</Tabs>

## Lifetimes

| Lifetime | Created | `Init(ctx)` runs | Notes |
|---|---|---|---|
| Singleton | Once, shared everywhere | During `BuildAll(ctx)` | The default for infrastructure |
| Scoped | Once per `Scope` | On first resolution in the scope, with the scope's context | One instance per HTTP request |
| Transient | Fresh on every resolution | Never | **Cannot implement `Service`** |

### Why transient services cannot implement `Service`

Because nothing would ever call `Close` on them. Singletons are recorded in
the container and scoped instances in their `Scope`, which is what lets each be
torn down. A transient is handed to the caller and no reference is kept, by
design. Allowing a managed lifecycle there would mean either retaining every
instance, making "transient" an unbounded leak, or never closing them at all.
Service names would collide too, since the kill-switch addresses services by
`Name()` and every transient instance shares one.

The rule is enforced with a panic at registration, because it is decidable from
the type alone.

<Aside type="note" title="Captive dependencies">
The mirror-image check runs at build time: a singleton may not depend on a
scoped or transient service. A longer-lived holder would pin a shorter-lived
instance and silently promote its lifetime, so the container rejects it with
`captive dependency: singleton X depends on scoped Y`.
</Aside>

## Service shape

A registered type that declares `Init` or `Close` must implement all three
methods:

```go
type Service interface {
	Name() string // Unique identifier, e.g. "gas/auth"
	Init(ctx context.Context) error  // Register routes, middleware, subscriptions
	Close(ctx context.Context) error // Clean up internal resources
}
```

The container rejects a type whose `Init` or `Close` lacks the context
parameter. For what the context carries, see
[Init and Close contexts](/gas/concepts/lifecycle/#init-and-close-contexts).

Anything short of that is rejected at startup with an error naming the missing
or mistyped methods, rather than registering cleanly and then never being
initialized. A type declaring none of them, or only `Name()`, is an ordinary
dependency and is unaffected.

## Resolving

```go
svc, err := container.Resolve[*auth.Service]()
svc := container.MustResolve[*auth.Service]()
```

`Resolve` and `MustResolve` are generic methods on both `*ServiceContainer` and
`*Scope`. Scoped services cannot be resolved from the container; resolve them
from a [scope](/gas/concepts/request-scopes/) instead.

### Resolution errors

`Resolve`, `BuildAll`, and startup return errors that wrap a sentinel, so
classify them with `errors.Is`. The message still names the types involved.

| Sentinel | Returned when |
|---|---|
| `gas.ErrNotRegistered` | A type, or a constructor's dependency, has no registration or instance |
| `gas.ErrCircularDependency` | Registered constructors depend on each other in a cycle, a constructor or `Init` resolves the type being built through a captured container or scope, two goroutines' builds would wait on each other, or constructors nest deeper than 256 |
| `gas.ErrCaptiveDependency` | A singleton depends on a scoped or transient service |
| `gas.ErrScopeRequired` | A scoped service is resolved from the container instead of a `Scope` |
| `gas.ErrInvalidLifetime` | A registration's `ServiceLifetime` is not Singleton, Scoped, or Transient |
| `gas.ErrInvalidServiceShape` | A registered type declares `Init` or `Close` but does not implement `Service` |
| `gas.ErrNoConstructor` | The container is asked to construct a type it has no constructor for. It guards an internal invariant and is not returned through the public API today |

```go
if _, err := container.Resolve[*auth.Service](); errors.Is(err, gas.ErrNotRegistered) {
	// register it, or resolve something else
}
```

`MustResolve` panics with a string that carries the same message.

The options passed to `NewApp` have imperative twins on the container, and
forwarded on the Worker, for wiring done after construction:

```go
c := w.ServiceContainer()
c.RegisterSingletonService[*auth.Service](auth.New)
svc := c.MustResolve[*auth.Service]()
```

Both forms share registrations and return the same instances.
