## What it is for

`gas/migrate` applies schema changes that individual services declare. Its
`*migrate.Service` implements `gas.MigrationManager`, the core interface a
service injects to register its migrations, along with `gas.Service`.

There is no central list of migrations. Each service registers its own while
it initializes, so a service carries its schema with it, and removing a
service removes its migrations. Once every service has initialized, the app
applies whatever is pending, from every service, in one global version order.
Applied migrations are recorded in a `__gas_migrations` table in the same
database.

It works on PostgreSQL, SQLite and MySQL, through a
[gas/database](/gas/modules/database/) provider or any other
`gas.DatabaseProvider`. On MySQL the DSN needs `parseTime=true`; see
[MySQL](#mysql).

## Usage

### Declaring migrations

registers its migrations in `Init`. Register before `Init` returns: pending
migrations are applied right after the last service initializes.

usually an `embed.FS`:

<Code code={region(mig, 'register-fs')} lang="go" title="notes/service.go" />

`RegisterFS` walks the whole file system, subdirectories included. Every file
ending in `.up.sql` is a migration, named `{version}_{description}.up.sql`:

- the version is the file name up to the first underscore, so a version must
  not contain one: `20260101_001_create_notes.up.sql` has version `20260101`;
- the description is the rest of the name with underscores turned into spaces
  (`create notes`);
- a matching `.down.sql` file is required, and a missing one fails
  `RegisterFS` with an error naming the `.up.sql` file. Nothing from that file
  system is registered then.

Every registration records the service it was given as the migration's owner,
and the owner's `Name()` is stored in the tracking table.

### Versions

Versions are compared as strings, so give them a fixed width, such as a
timestamp. Every pending migration from every service runs in one ascending
version order, and a version must be unique across the app. See
[Version rules](#version-rules).

### When migrations run

`gas.App` and `gas.Worker` both run them as part of `Start` (and so of
`App.Run`): after every service has initialized, before the app's ready
hooks, and before the HTTP server accepts traffic. `Start` calls `RunPending`,
which applies, in version order, every registered migration whose version is
not in the tracking table.

A failed migration stops the run and fails startup. See
[Transactions and failures](#transactions-and-failures).

### Fixing a dirty migration

A migration that fails is recorded as dirty, and the app does not start again
until you resolve it. To resolve it, fix the cause, then call
`ClearDirty(version)` on the `*migrate.Service`. It deletes the version's tracking row, so the next
`RunPending` applies the migration again. For a version that is not dirty,
because it applied cleanly or has no tracking row, it changes nothing and
returns an error wrapping `migrate.ErrNotDirty`.

`ClearDirty` is not part of `gas.MigrationManager`, and the app cannot start
while a version is dirty, so run it from a maintenance command that builds
the two services itself:

### Editing an applied migration

Each tracking row records a checksum of the up SQL it was applied with.
`RunPending` compares it with the registered up SQL on every start, also when
nothing is pending, and while they differ it applies nothing and fails with an
error wrapping `migrate.ErrChecksumMismatch` that names each version with its
stored and registered checksums. Editing the down SQL or the description is
fine; neither is part of the checksum.

When a migration was edited after it was applied:

1. Write a new migration instead. An applied migration is never edited, and
   that holds for Gas's own modules too: a module never edits a migration it
   has shipped.
2. In development, for the latest migration, call `Down(1)` and then
   `RunPending`. `Down` reverts the migration with its down SQL and deletes
   its row; `RunPending` applies the edited up SQL and records its checksum.
3. As a last resort, write the registered checksum from the error into the
   row by hand: `UPDATE __gas_migrations SET checksum = '<registered>' WHERE
   version = '<version>'`. Do it before rolling out the edited build.
   Instances of the previous build then fail `RunPending` on their next start
   until they are rolled forward, and rolling back to the previous build
   needs the `UPDATE` undone with the stored checksum from the error.

There is no option to accept an edit in code.

## Errors

| Error | Returned by | When |
|---|---|---|
| `migrate.ErrDirty` | `RunPending`, `Down`, `CheckReady` | Any version is marked dirty. The message names the versions |
| `migrate.ErrDuplicateVersion` | `RunPending`, `Down`, `CheckReady` | Two different migrations share a version. The message names the version and the services |
| `migrate.ErrNotDirty` | `ClearDirty` | The version is not marked dirty |
| `migrate.ErrChecksumMismatch` | `RunPending` | An applied migration's up SQL was edited. The message names each version, its owner, and the stored and registered checksums |

All four are returned wrapped; match them with `errors.Is`. Other errors
start with `gas/migrate:`, including the failure of a migration
(`... failed (marked dirty): <cause>`, wrapping the driver's error). Before
`Init`, `RunPending`, `Down`, `ClearDirty` and `CheckReady` return
`gas/migrate: not initialized`; after `Close`, `gas/migrate: service is
closed`. `Register`, `RegisterSlice` and `RegisterFS` work at any time.

## Behavior details

The sections above cover everyday use. This section is the full contract, for
when an exact edge case matters.

### Drivers

`Init` picks the SQL dialect for the tracking table from the provider's
`Driver()`:

| `Driver()` | Dialect |
|---|---|
| `postgres`, `pgx` | PostgreSQL |
| `mysql` | MySQL |
| `sqlite`, `sqlite3` | SQLite |

Any other driver name fails `Init` with `gas/migrate: unsupported driver`.
`Init` then creates `__gas_migrations` if it does not exist, under the
context `Init` receives. The module reads no configuration.

### MySQL

`gas/database` accepts `postgres`, `pgx` and `sqlite` as its own drivers.
For MySQL, give it a connector with `database.WithConnector` and set
`database.driver` to `mysql`, or register your own `gas.DatabaseProvider`
whose `Driver()` returns `mysql`; see [Database](/gas/modules/database/).

The MySQL DSN needs `parseTime=true`, because the module scans the tracking
table's `applied_at` column into `time.Time`. Without it the first
`RunPending` succeeds, but every later read of the tracking table fails:
`CheckReady`, `Down`, and the next `RunPending`, so the next start of the app.
The error is `gas/migrate: failed to query applied migrations: sql: Scan
error on column index 5, name "applied_at": unsupported Scan, storing
driver.Value type []uint8 into type *time.Time` (KI-048, see
[Known issues](/gas/project/known-issues/)).

### Version rules

Versions are strings and are compared as strings, so they must have a fixed
width to sort as numbers. A timestamp such as `20260101001` works; `9` sorts
after `10`. Every pending migration, from every service, runs in ascending
version order, so a version decides where a migration runs relative to other
services' migrations too.

A version must be unique across the app. When two services register the same
version, or one service registers two different migrations under one
version, `RunPending`, `Down` and `CheckReady` fail with an error that wraps
`migrate.ErrDuplicateVersion` and names the version and the services, and
nothing runs. A service that registers an identical migration (same version,
description, up SQL and down SQL) more than once gets it applied once.

### Transactions and failures

If `RunPending` fails, `Start` closes every service it initialized and
returns an error starting with `gas: migrations:`. The app does not start.

Each migration's up SQL and its tracking row commit in one transaction. When
the SQL or the tracking insert fails, the transaction rolls back, the version
is recorded as dirty, and `RunPending` stops and returns the error.
Migrations that committed earlier in the same run stay applied. The up and
down SQL run as a single `Exec` call, so whether a migration can hold several
statements depends on the driver.

<Aside type="caution" title="MySQL DDL is not transactional">
On MySQL, DDL such as `CREATE TABLE`, `DROP TABLE` and `ALTER TABLE` commits
any open transaction implicitly. A migration containing DDL is therefore not
atomic with its tracking row in either direction: a failure after the DDL
leaves the schema changed whatever the tracking table says.
</Aside>

### Dirty versions

A dirty version blocks the app. While any version is dirty, `RunPending`,
`Down` and `CheckReady` return an error wrapping `migrate.ErrDirty` that names
the dirty versions, so every later start fails until you resolve it. A dirty
migration's up SQL was rolled back (except for MySQL DDL), so the schema is
as it was before that migration.

### Rollback rules

`Down(n)` reverts the `n` highest versions in the tracking table, highest
first. For each, it runs the down SQL and deletes the tracking row in one
transaction. When either fails, that migration's transaction rolls back, the
version is not marked dirty, and `Down` stops and returns the error; versions
it reverted before the failure stay reverted. A version to revert must still
be registered, or `Down` fails with an error naming it. An `n` larger than
the number of applied migrations reverts them all; zero or less reverts
nothing. Like `RunPending`, `Down` runs nothing while any version is dirty,
because a dirty version's down SQL would act on a schema its up SQL never
changed.

### The tracking table

`__gas_migrations` has one row per applied or dirty version:

| Column | Holds |
|---|---|
| `version` | The migration version, the primary key |
| `service` | The owning service's `Name()` |
| `description` | The migration's description |
| `migrate_version` | The version of `gas/migrate` that applied it |
| `module_version` | The version of the Go module whose path ends in `/` plus the service name, such as `github.com/gasmod/gas/auth` for `gas/auth`; empty when there is none |
| `applied_at` | When the row was written |
| `dirty` | Whether the migration failed |
| `checksum` | The checksum of the up SQL the row was written for, or empty for a row written without one |

Both versions are read from the binary's build information.

### Checksums

The checksum is the SHA-256, in lowercase hex, of the migration's up SQL with
every CRLF replaced by LF, so a Windows checkout with `core.autocrlf` records
the same checksum; nothing else is normalized. It covers the whole up SQL,
`-- gas:` directives included, and not the down SQL or the description. A
migration registered with different SQL per database has a checksum per
database. Every row `RunPending` writes, clean or dirty, carries its
migration's checksum.

On every call, after the dirty check, `RunPending` first records the
registered checksum into each row of a registered version whose checksum is
empty, and logs `checksums recorded` with the count. It then compares each
row of a registered version that has a checksum, logs `checksum mismatch` at
warn level with both checksums for each difference, and fails with
`migrate.ErrChecksumMismatch` before applying anything. A dirty version takes
precedence: `RunPending` returns `migrate.ErrDirty` before it looks at
checksums. Rows of versions no service registers are never recorded or
checked. `Down` and `CheckReady` neither check nor record checksums.

### Upgrading the tracking table

A tracking table written by an earlier release has no `checksum` column.
`Init` adds it with `ALTER TABLE ... ADD COLUMN`, under the migration lock on
PostgreSQL and MySQL and in a `BEGIN IMMEDIATE` transaction on SQLite, and
logs `checksum column added`. On an existing table `Init` therefore needs
the right to alter it; on PostgreSQL that is ownership of the table. On
PostgreSQL and MySQL the `ALTER` waits for the table's lock for at most the
lock timeout or 5 seconds, whichever is shorter, and fails `Init` with
`gas/migrate: add checksum column:` and the driver's error when another
session holds the table longer.

Instances of v0.5 keep working against the upgraded table, the rows they
write get an empty checksum, and going back to v0.5 keeps working. The first
`RunPending` after the upgrade records the checksums of the existing rows
from the up SQL registered at that time and checks them from then on, so an
edit made before that run is not caught.

### Health and readiness

`*migrate.Service` implements `gas.ReadyReporter` but not
`gas.HealthReporter`. `CheckReady` fails when the service is closed or not
initialized, while any version is dirty (wrapping `migrate.ErrDirty`), when
two migrations share a version (wrapping `migrate.ErrDuplicateVersion`), and
while any registered migration has not been applied
(`gas/migrate: <n> pending migration(s)`). Once the app has started, the
last case means a migration was registered or reverted after `RunPending`
ran.
