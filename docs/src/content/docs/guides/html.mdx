Two modules, split along one line: `gas/template` decides **where template
source lives**, `gas/ui` decides **how it renders**. That separation is what
lets you develop against files on disk and ship a single binary with templates
embedded, without the rendering code noticing.

```bash
go get github.com/gasmod/gas/template github.com/gasmod/gas/ui
```

## Where templates come from

| Backend | Use it for |
|---|---|
| `template/fs` | An `fs.FS`. `os.DirFS` in development, `embed.FS` in a release binary |
| `template/dir` | A directory on disk, with an in-memory overlay for runtime additions. It declares `Close` but does not implement `gas.Service` (no `Name` or `Init`, and its `Close()` takes no context), so the container rejects a `*dir.Store` at startup with `gas.ErrInvalidServiceShape`. Pass it where a `gas.TemplateProvider` value is taken directly, such as inside a `template/composite` store, and close it yourself |
| `template/memory` | Tests and ephemeral content |
| `template/db` | Templates users can edit, across multiple instances |
| `template/composite` | Chain them: write to the first, read through all |

The composite store is the interesting one. Put a database store first and an
embedded store behind it, and you get user-editable templates that fall back to
the versions you shipped.

The `template/db` store's table is created by a migration, and migrations run
after every service has started. On a fresh database, write templates into it
from a ready function (`gas.WithReadyFunc`), not from another service's `Init`.

## Directory convention

<FileTree>
- templates/
  - layouts/
    - base.html the entry point, `{{define "base"}}`
  - partials/
    - nav.html parsed into every render
    - footer.html
  - home.html a page, rendered as `Render(w, "home", data)`
  - notes/
    - list.html nested pages work, `"notes/list"`
</FileTree>

Everything in `layouts/` and `partials/` is parsed into every render. Everything
else is a page. When `layouts/` holds any template, every page renders through
the layout's entry point (`base` by default), whether or not it defines blocks.
A page renders standalone only when there are no layouts at all.

## Template functions

Built in: `upper`, `lower`, `title`, `trimSpace`, `contains`, `hasPrefix`,
`hasSuffix`, `replace`, `join`, `split`, `truncate`, `now`, `formatTime`,
`formatTimePtr`, `add`, `sub`, `dict`, `list`, `json`, `env`, and `buildId`.

`dict` is the one you will use most, since it is how a partial gets arbitrary
data: `{{template "user-card" dict "Name" .UserName "Role" "admin"}}`.

`buildId` returns a stable id per process, and a fresh one per call in
development, which makes it a good cache-busting query parameter on asset URLs.

<Aside type="caution">
`title` maps to `strings.ToTitle`, which maps every letter to title case. On
ASCII input that means the whole string comes back uppercased, not
title-cased.
</Aside>

## Static files

Set `UI.StaticDir` (or pass `ui.WithStaticFS` for an `embed.FS`) and the service
registers a route serving it, with directory listing blocked. Three settings,
three separate jobs:

| Setting | Answers |
|---|---|
| `StaticDir` / `WithStaticFS` | **What** to serve |
| `StaticPath` / `StaticPaths` | **Where** to serve it, as URL patterns |
| `StaticStripPrefix` | **What to strip** before looking up the file |

When `StaticStripPrefix` is empty it defaults to the literal part of
`StaticPath` up to the wildcard, so the default `/static/*` strips `/static/`
and `/static/app.css` serves `app.css` from the root of the static directory. If
the FS mirrors your URLs instead (`static/app.css` at `/static/app.css`), set
`StaticStripPrefix: "/"` to strip nothing. With `StaticPaths` and no
`StaticStripPrefix`, nothing is stripped.

## Development mode

When `GasEnv` is development-like, templates rebuild on every request, so edits
show up on refresh. In production they are built once.
